The agent collects inventory and health of a device and reports them to your server. It **only reads**, opens **only outbound** connections and cannot run commands, scripts or files from the server. Nothing but the agent is installed on the devices; the commands use only what the operating system brings along.

## What the agent collects

| Area | Contents |
|---|---|
| System | host name, operating system and version, uptime |
| Hardware | manufacturer, model, serial number, CPU, memory, disks |
| Network | interfaces with MAC and IP addresses, throughput per interface |
| Software | installed programs with version and publisher; sent only when the list has changed |
| Health | load of CPU, memory, disks and, where the driver reports it, the graphics card |
| Security state | disk encryption, antivirus with the age of its signatures, firewall, automatic updates with the day of the last updates, Secure Boot and screen lock, each on, off, partly or unknown |
| Hyper-V | the guests on a Hyper-V host, once the connection "Hyper-V through agent" is set up ([Hypervisors](/en/pro/virtualisierung/)) |

The agent never collects file contents, browser histories, keyboard or screen data, connections or processes.

**Platforms:** Linux (x86-64, ARM64) with systemd and Windows (x86-64) as a service. An agent for macOS is planned.

**Security state:** On Windows the agent reads it through fixed WMI queries and the registry, on Linux from files only (dm-crypt, EFI variables, enabled services, the configuration of unattended-upgrades and dnf-automatic). It starts no program for this and reads no keys, rules, findings or update names. You see it on the asset's **Health** tab if you may see agents; a state older than three days no longer counts. The collector is called `security` and is on by default.

## Rolling out an agent

<Steps>

1. Open **Agents** and choose **Create rollout token**.

2. Set:
   - **Description**, for example a site or device group;
   - **Valid for (hours, at most 168)**, 24 by default;
   - **Maximum number of devices**;
   - **Location of the new assets (optional)**;
   - **Admit new agents only after approval**, if each device is to be confirmed.

   A token for **several devices without approval** is created only shortly after confirming your sign-in (one-time code or signing in again at the identity provider, valid for 5 minutes); the dialog offers it when you create the token. A token for one device or with approval needs none.

3. **Create token.** The token is **shown once**; the server keeps only its hash. Copy it now.

4. Choose the platform and copy the ready-made installation command. It downloads the agent from your server, checks the SHA-256 checksum and stops before installing if it differs.

5. Run the command on the device, as root on Linux, in a PowerShell as administrator on Windows. When the agent asks for the rollout token, paste it; the input stays hidden and appears neither on the command line nor in the history.

</Steps>

The agent first checks that it reaches your server and that the server's CA matches the fingerprint in the command, and only then asks for the token. Without a matching fingerprint it stops; there is no "trust on first use".

### Software distribution

For Ansible, scripts and similar tools, put the token beforehand into the file named in the command, owned by root with mode `0600` on Linux, readable only by SYSTEM and administrators on Windows. The agent refuses any other file. After a successful enrolment it deletes the file.

## Check the result

- The device appears under **Agents**, first as **pending** if approval is required. Approve it; without approval, the system blocks a pending agent after 7 days and revokes its certificate (the period can be set up to 30 days).
- After the first inventory the device appears as an asset with hardware, software and health.
- By default the list shows only agents that need attention (approval pending, no report for a day, certificate about to run out), all of them on request.

## Agent for an existing asset

If the device is in the inventory already, created by hand or as a virtual machine from the hypervisor, the agent should not create a second asset.

- **Before installing:** open the asset, tab **Condition**, and choose **Install an agent for this asset**. The rollout token then serves exactly one installation, and the agent reports as this asset. Because its reports change an existing asset, creating it needs a fresh confirmation of the sign-in; after signing in at the identity provider you return to the asset.
- **Merging afterwards:** if an agent created an asset of its own after all, its tab **Condition** asks **Is this device in the inventory already?** with possible matches (same name, host name, serial number or MAC address). **Move agent** connects the agent to the existing asset. Name, category and location of the target stay; host name, manufacturer, model, serial number and MAC addresses are kept up to date by the agent from then on. You can delete the previous asset in the same step.

The matches are suggestions only; nothing moves until a person confirms it.

## Device installed again

Every installation with a rollout token is a registration of its own; the old one does not sign off when it is uninstalled. When a device with the same host name registers again, the new registration is approved and the old one has not reported since, the older registration shows **Replaced by a newer registration** and the button **Replace**. It blocks the old one, and the new one takes over its asset with its history; the asset the new one created itself can be deleted at the same time. SentryAssets blocks nothing by itself, as the device names its host name itself. If the old registration keeps reporting, it is a second device of the same name, and there is no hint. An asset you chose for the new registration is never deleted. **Active** means registered and not blocked; an active agent that missed three heartbeats (15 minutes) shows **No heartbeat**. Blocked registrations have their own tab **Blocked**, and collectors carry the badge **Collector**: an agent and a collector on one host are two registrations, not a duplicate.

## Blocking

A blocked agent is refused at every request; its certificate is on the revocation list. A rollout token is **revoked** under **Agents** as well; devices already enrolled are not affected.

## Uninstalling an agent

When a device is retired or should no longer run an agent, the commands are under **Agents** on the card **Uninstall an agent**.

<Steps>

1. Block the agent under **Agents** with **Block**. Its certificate is then invalid and it can send no more data, even while it still runs. This cannot be undone; if the device is to get an agent again later, it enrols anew.

2. Remove it on the device with the command for its system, with administrator rights. The command stops the service and deletes the program, certificate and keys. It uses only what the operating system brings along.

   **Linux**, in a terminal as root or with `sudo`. Without either the command stops before it changes anything:

   ```bash
   (
     set -eu
     if [ "$(id -u)" -eq 0 ]; then as_root=""
     elif command -v sudo >/dev/null 2>&1; then as_root="sudo"
     else echo 'Run this as root, for example after su -' >&2; exit 1; fi
     $as_root systemctl disable --now sentryassets-agent
     $as_root rm -f /etc/systemd/system/sentryassets-agent.service
     $as_root systemctl daemon-reload
     $as_root rm -rf /opt/sentryassets-agent /var/lib/sentryassets-agent
   )
   ```

   **Windows**, in a PowerShell started as administrator:

   ```powershell
   Stop-Service SentryAssetsAgent -ErrorAction SilentlyContinue; sc.exe delete SentryAssetsAgent; Remove-Item -Recurse -Force (Join-Path $env:ProgramFiles 'SentryAssets\Agent'), (Join-Path $env:ProgramData 'SentryAssets\Agent') -ErrorAction SilentlyContinue
   ```

3. The asset stays with its history. Retire or delete it if the device is gone as well.

</Steps>

Block the agent before removing it: an agent deleted only on the device keeps a valid certificate until it expires. A collector is removed the same way, see [Uninstalling a collector](/en/guides/collector/#uninstalling-a-collector).

## Certificates and renewal

Each agent creates its own key pair (ECDSA P-256), which never leaves the device, and receives a certificate for 30 days. On Windows the key is kept in the TPM, on devices without one in the Windows key storage, non-exportable in both cases: a backup or image of the device holds no usable key. On Linux it is a file only the service can read. From day 20 it renews it itself, each time with a **new** key. Connections use only mTLS with TLS 1.3 against the CA pinned at enrolment.

As soon as the agent uses the new certificate, the old one is revoked. If such a revoked certificate is presented for an active agent afterwards, two parties hold the same identity: key and certificate were copied, for example from a backup, a snapshot or a compromised device, and the copy renewed first. SentryAssets then revokes all certificates of the agent at once, so the copy has no access either, and shortly afterwards, within an hour, blocks the agent itself. **Settings › Activity** shows **revoked certificate presented again** with the source address and the block with its reason. Enrol the device again with a new rollout token. A device you reset to a snapshot from before its last renewal looks the same and is blocked as well.

## Updates

Agents update themselves, but only to versions the vendor signed offline (Ed25519, keys built into the agent). A server taken over can therefore not distribute a foreign version.

- Only higher versions, never a step back; after the first offer each device waits a fixed time of up to 24 hours.
- Switch off on the server: `SA_AGENT_AUTO_UPDATE=false` in `.env`.
- Install at once on a Linux device:

  ```bash
  sudo /opt/sentryassets-agent/bin/sentryassets-agent update
  sudo systemctl restart sentryassets-agent
  ```

- Fallback: rename `sentryassets-agent.previous` (Linux) or `sentryassets-agent.exe.old` (Windows) back and restart the service.

## Hardening on the device

- **Linux:** systemd unit with a sandbox (among others `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `MemoryDenyWriteExecute`, a system call filter). Write access only to its own program directory and the state directory `/var/lib/sentryassets-agent`.
- **Windows:** a service; the state directory `%ProgramData%\SentryAssets\Agent` only for SYSTEM and administrators. Data through WMI with fixed, read-only queries, no PowerShell.
- The agent refuses to start if its directory or files are readable by others.

<Aside type="caution" title="Known limitations">
On Windows the private key is kept in CNG, in the TPM where there is one, not exportable; on Linux in a file with strict permissions. Windows binaries are not yet Authenticode-signed, which SmartScreen or virus scanners may report; set up [exclusions](#exclusions-in-virus-scanners-and-edr) for this reason.
</Aside>

## Exclusions in virus scanners and EDR

Virus scanners and EDR products (such as Microsoft Defender for Endpoint, CrowdStrike Falcon, SentinelOne or ManageEngine Endpoint Central) may classify the agent as an unknown program, quarantine and delete it, often while it is being downloaded or when it updates itself. Therefore, set up an exclusion for the program folder in your product's console **before rolling out**:

| System | Program folder (exclusion) | State folder |
|---|---|---|
| Windows | `C:\Program Files\SentryAssets\Agent\` with `sentryassets-agent.exe` | `C:\ProgramData\SentryAssets\Agent\` |
| Linux | `/opt/sentryassets-agent/bin/` with `sentryassets-agent` | `/var/lib/sentryassets-agent/` |

**Why the folder and not just the file:** during an update the agent replaces itself in its own program folder. It first stores the new version there as `.sentryassets-agent.update-…`, checks it, renames the running program (`sentryassets-agent.exe.old` on Windows, `sentryassets-agent.previous` on Linux) and puts the new file in its place; the service manager then restarts it. The installation command also downloads the program into this folder, first as `sentryassets-agent.exe.download`. To an EDR product this looks like a service swapping an executable, and it intervenes. An exclusion by checksum (hash) applies to one version only and ends with the next update; use the folder path if your product allows it, together with the program path as a process.

Notes:

- Keep the exclusion as narrow as possible: only the program folder, not `C:\Program Files\` or `/opt/` as a whole. Both folders are writable only by administrators or root; on Linux the agent checks this before every update.
- The state folder usually needs no exclusion. If the console reports blocked access to the certificate or key there, exclude it as well.
- Even with an exclusion the agent checks every update itself: it only accepts versions signed by the vendor (see [Updates](#updates)).
- The same applies to the [collector](/en/guides/collector/) with `/opt/sentryassets-collector/bin/`, and to the [directory agent](/en/guides/verzeichnis-agent/#exclusions-in-virus-scanners-and-edr) with its own folder.

## Troubleshooting

- **"Server not reachable":** the message names host and port. Check DNS, routes, firewalls and, if set, the device's proxy. TLS inspection by a proxy breaks mTLS on purpose; exempt the agent host there.
- **Clock:** certificates need a correct clock. The agent detects a deviation and reports it.
- **Enrolling again:** stop the service first (`sudo systemctl stop sentryassets-agent`) and start it again afterwards. The command from the rollout dialog does that itself.
- **Service does not start, "access denied":** see the following section.

### Service does not start: access denied

If a virus scanner or EDR product has quarantined the agent, it looks like this:

- The agent shows **No heartbeat** under **Agents**, often shortly after installation or after an update.
- `Start-Service SentryAssetsAgent` fails, `sc.exe start SentryAssetsAgent` reports `FAILED 5: Access is denied`.
- `Test-Path "$env:ProgramFiles\SentryAssets\Agent\sentryassets-agent.exe"` returns `False`, or the file cannot be opened.
- The Windows event log often shows nothing, because the EDR product intervenes itself and logs only in its own console.

How to fix it:

<Steps>

1. **Check the EDR product's console:** search the quarantine and the event or detection log for `sentryassets-agent` or the path of the program folder. It shows the time, the device and the rule that triggered. For managed products this view is in the central console, not on the device.

2. **Set up an exclusion** for the program folder as described under [Exclusions in virus scanners and EDR](#exclusions-in-virus-scanners-and-edr), and wait until the policy has reached the device.

3. **Bring the program back:**
   - If `sentryassets-agent.exe.old` is still in the program folder after an update, rename it back to `sentryassets-agent.exe` and start the service with `Start-Service SentryAssetsAgent`. The agent then updates again, this time with the exclusion in place.
   - Otherwise restore the file from quarantine and start the service.
   - If neither works, run the installation command again with a new rollout token. It downloads and checks the program anew. The device is then a new registration; take over the previous asset with **Replace** (see [Device installed again](#device-installed-again)).

4. **Check the result:** `Get-Service SentryAssetsAgent` shows `Running`, and after a few minutes the agent is **Active** again under **Agents**.

</Steps>

On Linux the same shows up as `Permission denied` or a missing file in `journalctl -u sentryassets-agent`; set up an exclusion for `/opt/sentryassets-agent/bin/`, rename `sentryassets-agent.previous` back or install again, then `sudo systemctl restart sentryassets-agent`.
