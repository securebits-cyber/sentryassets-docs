The collector finds devices that run no agent: printers, switches, phones, IoT devices. It is a program of its own for Linux, runs **without root rights** and scans only the networks you allow on site. One collector per network segment is enough.

## How the scan works

- Per address one TCP connection attempt to a fixed list of ports: 22, 80, 443, 445, 515, 554, 631, 3389, 8080, 8443, 9100. The collector sends nothing and closes each connection at once. It reads no banners, sends no ICMP and uses no raw sockets.
- It reads the MAC address from the ARP table (only in its own segment) and the name through reverse DNS from the system's resolver.
- Limits: at most 32 attempts at a time and 200 per second. Scans are 1 to 24 hours apart, 4 hours by default.

## Allowed networks

You set the networks when setting up the collector on its machine. The server can only narrow this list, never widen it.

- at most 8 networks, each at most a /22 (1,024 addresses), 4,096 addresses together;
- private IPv4 ranges only (RFC 1918 and 100.64.0.0/10), without overlap. For 100.64.0.0/10 the collector warns, as it is often a provider's network.

When setting up, the web UI offers the host's networks to tick, see [Setting up a collector](#setting-up-a-collector).

A collector can thus serve neither as a tool against the internet nor as a stepping stone into networks nobody on site allowed.

## Setting up a collector

<Steps>

1. The easiest way starts from a Linux host on which an agent already runs. The page **Network** lists such hosts under **Hosts for a collector**; choose **Set up as collector** there. On the asset's page the same button is called **Set up as collector for this network**.

   Without an agent, open **Agents › Create rollout token** and choose the kind **Collector**.

2. Choose the **Location (required)**. Devices found propose this location; a collector cannot be set up without one. If there is exactly one location, it is already filled in; you can change the choice. If there is no location yet, create the first one right in the dialog, for example for your headquarters. If you lack the right to do so, ask your administration to create one under **Master data › Locations**.

3. Tick the networks under **Networks the collector may scan**. Offered are the private networks of the host's network adapters; preselected is what fits the limits together. Interfaces of containers (such as Docker), virtual machines and VPNs are not offered and are named under “Not offered”: a scan there finds no devices of the network.

   If a network is larger than a /22, such as a /21, the dialog offers only the section of 256 addresses (/24) around this host and says so: the collector will not find devices outside it. You add further sections under **Advanced**.

   A network the host does not show goes under **Advanced** into **More networks by hand (optional)**. Without an agent you enter all networks that way. Write a network as its first address and its size (CIDR notation), such as `192.168.10.0/24`: the addresses 192.168.10.0 to 192.168.10.255. The number after the slash gives the size: /24 is 256 addresses, /23 is 512, /22 is 1,024, and no larger.

4. **Advanced** also holds **Valid for (hours)** and **Number of devices**, preset to 24 hours and 1 device. For one host you need not change them.

5. Choose **Create token**. If the button is locked, the dialog says below it what is missing, such as “Choose a location first; then the token can be created.”

   A collector token is created only shortly after confirming your sign-in (one-time code or signing in again at the identity provider, valid for 5 minutes), since a collector scans networks and feeds findings in. The dialog offers the confirmation when you create the token.

6. Copy the installation command and run it on the machine. It checks the networks and the checksums and creates an unprivileged user of its own for the collector.

7. Approve the collector under **Agents** if the token requires approval. Under **Network** you choose which of the allowed networks it scans and how often.

</Steps>

## Matching findings

The page **Network** lists the devices found and matches them with the inventory, in this order:

1. MAC address (globally unique ones only, no random ones);
2. name, full or short, with the host name and name of the asset;
3. address with the interfaces of the agents.

Exactly one match links the device, several are a conflict, none means "new". You can **take a device over as an asset** (with a proposed category and the collector's location), link it to an asset, unlink it or ignore it, each with "Undo". A device found by several collectors appears once. Matching never changes assets by itself.

Only one collector's findings are shown by the link **View n findings** in its card at the bottom of the page; **Show all collectors** goes back.

## SNMPv3 and LLDP

For switches, routers and printers the collector reads on request over SNMPv3 the system, the chassis (manufacturer, model, serial number, firmware), the MAC addresses and names of the interfaces, the LLDP neighbours and the VLANs of each physical port: the untagged VLAN and the tagged ones, with the names the switch gives them.

- up to 4 SNMPv3 users per collector, **authPriv with SHA-2 and AES** only, passphrases of at least 20 characters (generated on request);
- stored encrypted and sealed so that only their collector receives them; it keeps them in memory only;
- a user can be limited to some of the collector's networks; a device that has answered is asked with its own user only;
- only devices the same scan found, with a fixed budget of requests per device;
- never devices with a SentryAssets agent of their own: they are PCs and servers, not network equipment, and a taken-over endpoint must not use the requests to guess passphrases. So let the passphrases be generated rather than choosing your own.

The VLANs show at the device under **Discovery › Network** and at the port in the rack. They come from the Q-BRIDGE-MIB, which most managed switches answer, and for Cisco switches without it from Cisco's own tables (access VLAN, native VLAN and allowed VLANs on a trunk). A device with neither shows no VLANs. If a switch has more than one query reads, it says “not all read”: what is shown is right, only a part is missing.

Under **Racks** you take a switch's interfaces over as ports in one click; LLDP neighbours appear there as cable suggestions. Nothing is cabled by itself; see [Racks and ports](/en/guides/racks/#ports-and-cables).

<Aside>
Set up an SNMPv3 user with read rights only on the devices. SentryAssets never writes over SNMP.
</Aside>

## Uninstalling a collector

<Steps>

1. Block the collector under **Agents** with **Block**. Its certificate stops working immediately and it no longer scans. If it had SNMPv3 users, change their passphrases on the devices: it knew them until now.

2. Remove it on its host in a terminal with `sudo`. The command is under **Agents** on the card **Uninstall an agent**, under **Collector**; it stops the service, deletes the program, certificate and keys and also removes the collector's system user.

   ```bash
   sudo systemctl disable --now sentryassets-collector && sudo rm -f /etc/systemd/system/sentryassets-collector.service && sudo systemctl daemon-reload && sudo rm -rf /opt/sentryassets-collector /var/lib/sentryassets-collector && sudo userdel sentryassets-collector
   ```

</Steps>

The collector's findings are no longer visible afterwards; assets you took over from them stay in the inventory.

## Troubleshooting

- **No MAC addresses:** the collector is in another segment than the devices. The ARP table only knows its own segment; set up a collector of its own there.
- **A scan reports nothing:** a blocked collector or one not yet approved does not scan. An invalid stored choice of networks scans nothing rather than everything, on purpose.
