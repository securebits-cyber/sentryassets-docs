A backup holds the database, the documents and the files of the agent PKI in **one** file, encrypted with the master key. It also moves the installation to another server.

## In the dashboard

Under **Settings › Backup** you do everything without a console. Only the administration of the installation sees the page; it is part of the Community Edition.

- **Back up now** makes a backup at once.
- **Schedule:** once a day at the chosen time, with the number of scheduled backups to keep (1 to 90). The service removes older scheduled ones after each new one; backups made by hand, by command and safety backups stay until you remove them. Recommended: daily at 2 a.m., 14 backups.
- **Check** reads and decrypts a file completely without changing anything. Only checked backups can be restored.
- **Download** saves a file on your computer, for example for off-site storage. The page lists every download; the bell reports it to every administrator for seven days.
- **Restore** replaces all data with the state of the backup, see below.

Schedule, download and restore need a fresh confirmation of the sign-in (TOTP or a new sign-in at the identity provider). The work is done by the service `backup-runner`, which starts with `docker compose up -d`; if it does not answer, the page says so. The bell warns when there is no backup, an old or a failed one; under **Profile** you can subscribe to these by e-mail (category “Backup of the installation”).

### Restoring in the dashboard

<Steps>

1. Choose **Restore** at a **checked** backup and type the name of your organisation to confirm.

2. The backup service checks the file again and then stops API, agent gateway and worker (maintenance). SentryAssets is unavailable for a few minutes; agents wait and send again afterwards.

3. First it makes a **safety backup** of the current state. Should the restore fail, it brings this copy back by itself. If the service is stopped halfway, it continues with the safety backup at its next start.

4. Afterwards the application starts by itself; everyone signs in again. The page takes you to the sign-in.

</Steps>

Then repeat what happened since the backup (see below). A backup from a newer version cannot be restored.

## By command

```bash
docker compose run --rm backup create --keep 14   # new backup, the 14 newest are kept
docker compose run --rm backup list               # backups in the volume backups
docker compose run --rm backup verify <name>      # full check without writing anything
docker compose run --rm -T backup create --stdout > sentryassets.sabak   # straight to the host
```

- Without the backup service, best every night from a timer or cron job, for example:

  ```bash
  0 2 * * * cd /opt/sentryassets/deploy/compose && docker compose run --rm backup create --keep 14
  ```

- Copy the files to another system regularly.
- **System health** shows the last backup and warns when it is missing, older than two days or a later one failed.
- Every backup and restore is recorded in the audit log.

<Aside type="danger" title="No restore without the master key">
The backup is encrypted with `./secrets/master_key`. Keep the key apart from the backups. No backup contains the key of the root CA (`root-ca.p12`); it stays offline.
</Aside>

## The master key

The master key is a file on the server: `deploy/compose/secrets/master_key` (from within `deploy/compose`, `./secrets/master_key`). It is created at installation when `scripts/generate-secrets.sh` runs and holds 32 random bytes in Base64. You do not download it anywhere; to move, you copy this file along.

Right after installing, keep a copy apart from the backups, such as in a password manager or on a medium in a safe. If the server is lost and the copy is missing, nobody can read a backup.

```bash
cat deploy/compose/secrets/master_key   # show the content to store it safely
```

## Moving to another server

<Steps>

1. Prepare the installation on the new server as described under [Installation](/en/guides/installation/), up to and including `generate-secrets.sh` and `docker compose build`.

2. Copy `./secrets/master_key` from the old server to the same place on the new one, overwriting the file `generate-secrets.sh` created there. The other secrets may be new. For example, from the old server:

   ```bash
   scp deploy/compose/secrets/master_key new-server:sentryassets/deploy/compose/secrets/master_key
   ```

   Adjust path and user to your installation. The `secrets` directory stays accessible only to the user who runs SentryAssets (`chmod 700`).

3. Start **only** the database and restore the backup:

   ```bash
   docker compose up -d postgres
   docker compose run --rm -T backup restore - < sentryassets.sabak
   docker compose up -d
   ```

4. `cli setup` and `cli pki init` are not needed; both come from the backup. Agents find the new server as soon as `SA_AGENT_HOST` points to it in DNS. Everyone signs in again.

</Steps>

- A backup is restored only into an **empty** database, with the same or a newer version. If `docker compose up` already ran on the new server, remove the database volume first (`docker compose down` and `docker volume rm sentryassets_postgres-data`).
- Before it commits, the restore checks every foreign key. The command names date and age of the backup.
- Afterwards repeat what happened since the backup: block agents, rollout and status tokens again, deactivate accounts again, set changed passwords of local accounts again or reset their access. Agents that renewed their certificate after the backup enrol again with a new rollout token.
- Restore only backups from your own storage: anyone with the master key can build a valid file.

## Renewing the agent PKI

The issuing CA and the certificate of the agent endpoint are valid for one year; **System health** warns 60 days before. They are renewed with the root key from the offline medium:

```bash
docker compose run --rm -v /media/offline:/offline:ro cli pki rotate --root-key /offline/root-ca.p12
docker compose restart caddy
```

The command asks for the passphrase and issues both again for the same names. **Restart the proxy by the time the command names**, usually 24 hours later. Until then the previous issuing CA keeps issuing, and it stays valid until it ends, so no agent drops out. If the command reports that the files were not all replaced, do not restart the proxy and run the command again.

## Checking the audit chain

```bash
docker compose run --rm cli audit verify
```

The job worker also checks the chain regularly; **System health** shows when it last did.
