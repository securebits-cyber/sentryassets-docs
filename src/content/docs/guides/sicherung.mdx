Eine Sicherung enthält die Datenbank, die Dokumente und die Dateien der Agent-PKI in **einer** Datei, verschlüsselt mit dem Master-Schlüssel. Mit ihr ziehen Sie auch auf einen anderen Server um.

## Im Dashboard

Unter **Einstellungen › Sicherung** erledigen Sie alles ohne Konsole. Die Seite sieht nur die Administration der Installation; sie gehört zur Community-Edition.

- **Jetzt sichern** legt sofort eine Sicherung an.
- **Zeitplan:** einmal am Tag zur gewählten Uhrzeit, dazu die Zahl der geplanten Sicherungen, die bleiben (1 bis 90). Ältere geplante entfernt der Dienst nach jeder neuen; Sicherungen von Hand, per Befehl und Sicherheitskopien bleiben, bis Sie sie entfernen. Empfehlung: täglich um 2 Uhr, 14 Sicherungen.
- **Prüfen** liest eine Datei vollständig und entschlüsselt sie, ohne etwas zu ändern. Nur geprüfte Sicherungen lassen sich wiederherstellen.
- **Herunterladen** speichert eine Datei auf Ihrem Rechner, etwa für die Ablage außer Haus. Die Seite listet jedes Herunterladen; die Glocke meldet es allen Administratorinnen und Administratoren sieben Tage lang.
- **Wiederherstellen** ersetzt alle Daten durch den Stand der Sicherung, siehe unten.

Zeitplan, Herunterladen und Wiederherstellen verlangen eine frische Bestätigung der Anmeldung (TOTP oder erneute Anmeldung beim Identitätsanbieter). Die Arbeit macht der Dienst `backup-runner`, der mit `docker compose up -d` startet; meldet er sich nicht, sagt die Seite das. Die Glocke warnt, wenn keine, eine alte oder eine fehlgeschlagene Sicherung vorliegt; die Meldungen lassen sich unter **Profil** als E-Mail abonnieren (Kategorie „Sicherung der Installation“).

### Im Dashboard wiederherstellen

<Steps>

1. Wählen Sie bei einer **geprüften** Sicherung **Wiederherstellen** und geben Sie zur Bestätigung den Namen Ihrer Organisation ein.

2. Der Sicherungsdienst prüft die Datei noch einmal und hält dann API, Agent-Gateway und Worker an (Wartungsmodus). SentryAssets ist einige Minuten nicht erreichbar; Agents warten und senden danach weiter.

3. Vorher legt er eine **Sicherheitskopie** des jetzigen Stands an. Scheitert die Wiederherstellung, spielt er diese Kopie automatisch zurück. Wird der Dienst mittendrin beendet, setzt er beim nächsten Start mit der Sicherheitskopie fort.

4. Danach startet die Anwendung von selbst; alle melden sich neu an. Die Seite führt Sie zur Anmeldung.

</Steps>

Wiederholen Sie danach, was seit der Sicherung geschah (siehe unten). Eine Sicherung aus einer neueren Version lässt sich nicht einspielen.

## Per Befehl

```bash
docker compose run --rm backup create --keep 14   # neue Sicherung, die 14 neuesten bleiben
docker compose run --rm backup list               # Sicherungen im Volume backups
docker compose run --rm backup verify <Name>      # vollständig prüfen, ohne etwas zu schreiben
docker compose run --rm -T backup create --stdout > sentryassets.sabak   # direkt auf den Host
```

- Ohne den Sicherungsdienst am besten jede Nacht per Timer oder Cron, etwa:

  ```bash
  0 2 * * * cd /opt/sentryassets/deploy/compose && docker compose run --rm backup create --keep 14
  ```

- Kopieren Sie die Dateien regelmäßig auf ein anderes System.
- Die Seite **Systemzustand** zeigt die letzte Sicherung und warnt, wenn sie fehlt, älter als zwei Tage ist oder eine spätere scheiterte.
- Jede Sicherung und Wiederherstellung steht im Audit-Log.

<Aside type="danger" title="Ohne Master-Schlüssel keine Wiederherstellung">
Die Sicherung ist mit `./secrets/master_key` verschlüsselt. Bewahren Sie den Schlüssel getrennt von den Sicherungen auf. Den Schlüssel der Root-CA (`root-ca.p12`) enthält keine Sicherung; er bleibt offline.
</Aside>

## Der Master-Schlüssel

Der Master-Schlüssel ist eine Datei auf dem Server: `deploy/compose/secrets/master_key` (aus dem Verzeichnis `deploy/compose` heraus `./secrets/master_key`). Sie entsteht bei der Installation, wenn `scripts/generate-secrets.sh` läuft, und enthält 32 Zufallsbytes in Base64. Sie laden ihn nirgends herunter; für einen Umzug kopieren Sie diese Datei mit.

Legen Sie gleich nach der Installation eine Kopie getrennt von den Sicherungen ab, etwa im Passwort-Manager oder auf einem Datenträger im Tresor. Ist der Server verloren und die Kopie fehlt, kann niemand eine Sicherung lesen.

```bash
cat deploy/compose/secrets/master_key   # Inhalt anzeigen, um ihn sicher abzulegen
```

## Auf einen anderen Server umziehen

<Steps>

1. Bereiten Sie auf dem neuen Server die Installation vor wie unter [Installation](/guides/installation/) beschrieben, bis einschließlich `generate-secrets.sh` und `docker compose build`.

2. Kopieren Sie `./secrets/master_key` vom alten Server an dieselbe Stelle des neuen und überschreiben Sie damit die Datei, die `generate-secrets.sh` dort angelegt hat. Die übrigen Geheimnisse dürfen neu sein. Etwa vom alten Server aus:

   ```bash
   scp deploy/compose/secrets/master_key neuer-server:sentryassets/deploy/compose/secrets/master_key
   ```

   Pfad und Benutzer passen Sie an Ihre Installation an. Das Verzeichnis `secrets` bleibt nur für den Benutzer zugänglich, der SentryAssets betreibt (`chmod 700`).

3. Starten Sie **nur** die Datenbank und spielen Sie die Sicherung ein:

   ```bash
   docker compose up -d postgres
   docker compose run --rm -T backup restore - < sentryassets.sabak
   docker compose up -d
   ```

4. `cli setup` und `cli pki init` entfallen; beides kommt aus der Sicherung. Die Agents finden den neuen Server, sobald `SA_AGENT_HOST` per DNS auf ihn zeigt. Alle Personen melden sich neu an.

</Steps>

- Wiederhergestellt wird nur in eine **leere** Datenbank, mit derselben oder einer neueren Version. Lief auf dem neuen Server schon `docker compose up`, entfernen Sie vorher das Volume der Datenbank (`docker compose down` und `docker volume rm sentryassets_postgres-data`).
- Vor dem Abschluss prüft die Wiederherstellung jeden Fremdschlüssel. Der Befehl nennt Datum und Alter der Sicherung.
- Wiederholen Sie danach, was seit der Sicherung geschah: gesperrte Agents, Rollout- und Status-Tokens erneut sperren, deaktivierte Konten erneut deaktivieren, geänderte Passwörter lokaler Konten erneut setzen oder Zugänge zurücksetzen. Agents, die ihr Zertifikat nach der Sicherung erneuert haben, melden sich mit einem neuen Rollout-Token wieder an.
- Spielen Sie nur Sicherungen aus Ihrer eigenen Ablage ein: Wer den Master-Schlüssel hat, kann eine gültige Datei bauen.

## Agent-PKI erneuern

Issuing-CA und Zertifikat des Agent-Endpunkts gelten ein Jahr; der **Systemzustand** warnt 60 Tage vorher. Erneuert wird mit dem Root-Schlüssel vom Offline-Datenträger:

```bash
docker compose run --rm -v /media/offline:/offline:ro cli pki rotate --root-key /offline/root-ca.p12
docker compose restart caddy
```

Der Befehl fragt die Passphrase ab und stellt beides für dieselben Namen neu aus. **Starten Sie den Proxy bis zu dem Zeitpunkt neu, den der Befehl nennt**, in der Regel 24 Stunden später. Bis dahin stellt die bisherige Issuing-CA aus, und sie bleibt gültig, bis sie endet; so fällt kein Agent heraus. Meldet der Befehl, dass die Dateien nicht vollständig ersetzt sind, starten Sie den Proxy nicht neu und führen Sie den Befehl erneut aus.

## Audit-Kette prüfen

```bash
docker compose run --rm cli audit verify
```

Der Job-Worker prüft die Kette außerdem regelmäßig; der **Systemzustand** zeigt, wann zuletzt.
